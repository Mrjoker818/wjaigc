# 品牌、精修与字境预校验扣费审计

日期：2026-08-31。基线main `9f4a8f481519a6969e1347fd5a97a32b81298ec7`，生产源码仍9b2e8d5f；V5.8.8参考目录只读。状态：发现未修复的P0候选账务风险，禁止据此宣布发布通过。

## 验证方式

执行两个版本原始完整POST入口，以及各自原始credits、credit-pricing、credits-constants、api-validator、model-capabilities和字体常量模块；只转译，不改写路由分支。供应商查找、认证与SQL执行边界隔离：测试用户初始余额1000，数据库成功扣除/退款由内存SQL适配器模拟，网络、后台任务及非预期依赖调用一律禁止。

因此证明的是“原控制流会发出扣费SQL并在返回拒绝时遗漏退款SQL”，**不是真实PostgreSQL账单、云端用户受损或并发退款验证**。不访问业务数据库、不提交供应商、不改账号积分。中间件和真实模型授权边界不在此诊断内。

首次运行donor因媒体网关导入未隔离而有9个工具错误，保留first-run.json，不计为业务失败。补齐严格禁止调用的网关桩，并加载donor真实输入合同后，两次完整运行均18项、7通过/11失败、工具错误0，重复结果一致。失败不是11个独立Bug。

## 根因与去重

统一登记`V588-PROVIDER-003-BUG-006`：业务预校验位于consumeCredits之后，直接return 400不进入外层catch退款。品牌route.ts:498/505/507，精修route.ts:937/944/962，字境generate-image/route.ts:137/163/202。catch抛异常退款对照通过，排除“测试桩完全无法退款”的假象。

git blame显示相关顺序和直接返回来自dc5983d9；144f9b6ec仅为扣费调用增加providerId参数。不是9b2e8d5f结果来源/重试补丁引入。此问题发生在任务创建前，与异步终态/取消退款、供应商显式选择回退OBS-002/003/006、前端错误显示BUG-002/003分别登记，不重复算作同一Bug。

## 对吸收方案的影响

donor的visual-design-tools-contract.ts:161提前拒绝字境空输入是可参考的优点；但直接throw被外层catch转成500，不能整块移植该合同。品牌空描述原版已有正确400，donor在这条路径反而退化。供应商无可用项和精修缺模型的顺序仍需在当前架构修复。

推荐最小方案：仅在三个原路由把无副作用的输入、模型和可用供应商预检查移到首次扣费之前，保留已有成功请求、别名、提示词、数量及异步执行行为；无效请求返回现有400且不调用扣费。暂不改变显式/自动供应商策略，那是独立OBS边界。

替代方案：在每个提前返回前补退款。改动看似小，但会制造本可避免的扣费流水，并依赖退款成功，不推荐。全局重写账务引擎/迁移数据库则范围过大，本项不采用。

本建议尚未批准、未实施。应先于待批准的BUG-005前端辅助配对补丁处理，作为原PROVIDER-003验收发现的前置风险，不重开Stage4、不提前批次B。必须把这些失败用例转为永久路由回归，覆盖合法请求无回归，再执行隔离PostgreSQL、全量门禁及Chrome原预览验收；不以本次模拟SQL结果替代真实数据库验证。
