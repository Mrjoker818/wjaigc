# V588-ADMIN-004 管理员用户真实投影设计

> 状态：根因、Coze 云端 RED 与设计已确认；因 `V588-STABILITY-002` 为未关闭 P0，本项按风险顺序排在其云端闭环之后实施。

## 目标

让管理员“用户管理”与积分管理、数据管理、项目数据使用同一批真实用户身份和权威数据源，消除用户数量一致但积分、项目数、最后活动时间为假 0 或缺失的问题。

本项只修复管理员用户列表的读取投影，不改用户创建、删除、密码、模型授权、积分扣费、项目持久化或审计写入逻辑，也不复制 V5.8.8 的用户存储与逐用户查询实现。

## 已确认根因

当前 `GET /api/admin/users` 对 `dbGetUserData()` 的返回契约理解错误。该函数直接返回 `data_value`，路由却要求返回值包含 `data_value` 属性，因此项目数和旧积分读取分支不会执行。

积分的权威来源实际是 `wujie_credits`，不是 `wujie_user_data`。当前路由也没有读取审计或用户数据更新时间，导致 `last_login` 对所有用户缺失。

2026-08-27 Coze 云端真实 RED：

- 用户管理、积分管理、数据管理和仪表盘均识别 `6` 个用户。
- 管理员在用户管理中显示 `0` 积分，积分管理显示 `403`。
- 两个用户在用户管理中显示 `0` 个项目，数据管理分别显示 `1` 和 `10` 个项目。
- `6/6` 用户缺少最后活动时间。

## 方案选择

### 方案 A：批量权威投影，推荐

`listManagedUsers()` 继续负责用户身份。路由用固定数量的批量查询读取积分、项目 JSON 和活动时间，再通过纯函数合并。用户数量增加时不会线性增加 SQL 次数。

优点：数据源正确、无 N+1、容易测试、保持现有响应结构。缺点：需要增加一个小型投影模块和批量查询契约。

### 方案 B：把聚合逻辑全部放入 `db-storage.ts`

优点：路由较薄。缺点：会继续扩大已有大型存储文件，并把管理员专用投影混入通用数据访问层。

### 方案 C：直接复制 donor 的逐用户查询

优点：代码差异小。缺点：每个用户至少增加积分、项目和活动三次查询，规模扩大后明显变慢；同时复制 donor 的静默失败行为，会再次把存储错误伪装成 0。

采用方案 A。

## 数据源与返回契约

### 用户身份

继续使用 `listManagedUsers()`。它决定用户集合、用户角色、状态和名称；任何统计表都不能自行发明用户或删除没有统计行的用户。

### 积分

从 `wujie_credits` 按全部用户 ID 一次性读取 `user_id` 与 `balance`。没有积分行的真实用户余额为 `0`。

### 项目数

从 `wujie_user_data` 一次性读取 `data_key = 'projects'` 的 `user_id` 与 `data_value`。兼容：

- JSON 数组：数组长度。
- 历史 JSON 对象：顶层键数量。
- JSON 字符串：解析后再按上述规则计算。
- 空值或畸形值：项目数为 `0`，但不能影响其他用户。

### 最后活动时间

最后活动时间取以下三个来源中的最大有效毫秒时间戳：

1. `wujie_audit_log.created_at` 的用户最大值。
2. `wujie_user_data.updated_at` 的用户最大值。
3. 管理用户记录自身的 `updatedAt` / `updated_at`。

返回字段继续使用现有 `last_login`，值允许 `number` 或缺省；没有真实活动证据时不伪造当前时间。

### 覆盖信息

响应增加向后兼容的 `projectionCoverage`：

```json
{
  "identity": "available",
  "credits": "available",
  "projects": "available",
  "activity": "available"
}
```

现有 `success` 和 `users` 字段保持不变。数据库未配置时，用户身份仍可返回，但三项投影标记为 `unavailable`，不得声称这些 0 是数据库真实值。

## 组件边界

新增 `src/lib/admin-user-projection.ts`：

- 定义批量查询行类型。
- 安全解析项目数据。
- 以纯函数把用户、积分、项目与活动行合并为响应用户。
- 不执行 SQL、不读取请求、不处理管理员授权。

调整 `src/app/api/admin/users/route.ts`：

- 保留现有管理员授权和 POST 行为。
- GET 对非空用户集合执行固定三组批量查询。
- 数据库查询失败时返回明确的 `ADMIN_USER_PROJECTION_FAILED`，不能静默回退为全部 0。
- 数据库未配置时返回身份集合与 `unavailable` 覆盖状态。

调整 `src/components/dashboard/admin-tabs.tsx` 的类型，使 `last_login` 同时接受字符串和毫秒时间戳；不改变布局和按钮。

## 错误处理

- 未登录或非管理员：保持现有 `403`。
- 用户列表读取失败：保持 `500`。
- 数据库已配置但批量投影查询失败：`500`，返回 `code: ADMIN_USER_PROJECTION_FAILED`。
- 单个用户项目数据畸形：仅该用户项目数为 `0`，其余投影继续返回。
- 不记录 API Key、密码、Cookie 或完整隐私数据。

## 测试与验收

### RED / GREEN

1. 管理员用户列表从权威积分表读取余额。
2. 原始数组、对象和字符串项目数据得到正确项目数。
3. 最后活动时间选择审计、数据更新时间和用户更新时间的最大值。
4. 没有积分/项目行的用户仍出现且真实为 0。
5. 查询次数固定，不随用户数量增加。
6. 投影查询失败返回明确错误，不伪造 0。
7. 数据库未配置时返回 `unavailable` 覆盖状态。
8. 非管理员不执行投影查询。
