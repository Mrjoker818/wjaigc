# 302 放大未知提交的刷新恢复设计（2026-09-28）

状态：设计候选，未实施或放行。延续[图像编辑来源与冻结报价裁定](2026-09-28-image-edit-source-and-quote-decision.md)，只处理已确认报价的 302 放大请求；自动/非 302、其他动作和三个工作区的完整报价仍按原计划开放。Pear 分层不参与，PSD 核心不变。

## 问题与目标

浏览器已确认报价并发送付费 POST 后，断网、刷新或组件卸载都可能使前端丢失响应。服务端同键重放只在 `cloud_tasks` 已存在时可定位原任务；任务是在来源、模型及报价校验后才原子创建。因此“目前查不到任务”不能证明原请求不会稍后落库。目标是在刷新及跨标签后仍能按当前认证用户找到原尝试，且不能因响应丢失生成新幂等键、二次扣费或二次供应商提交。

## 方案比较与选择

1. 浏览器保存整个报价令牌和请求，刷新后重发：可以继续执行，但把短期付费授权放入持久存储；拒绝。
2. 从最近任务列表按图片/时间猜测：列表有条数上限，且不能证明同一次提交；拒绝。
3. 浏览器只保存随机幂等键及最小来源定位，服务端按当前 actor 精确只读查询：能恢复已建任务，查不到时安全地保持待核对；采用。它不依赖客户端提供“已付款”标志，也不允许查无任务时创建任务。

## 边界合同

- 报价确认前从现有 `/api/auth/me` 获取当前 actor。付费 POST **之前**将非敏感尝试标记持久写入浏览器存储：版本、actor、项目、源图片/版本标识、随机幂等键、创建时间；不存报价令牌、API Key、请求正文或图片数据。写入失败则不发付费 POST。按随机键各存一项，避免多标签覆盖。
- 页面加载后先确认当前 actor，再读取属于该 actor/项目的未决标记。恢复检查期间及存在未决标记时，不得为同一源图取得新付费报价/新键。其他用户的标记不得显示或阻断其操作；认证不可用时维持安全阻断，不假设是旧用户。
- 在现有 `GET /api/tasks/recover` 增加 `projectId` + `idempotencyKey` 精确只读分支：当前认证 actor + 精确幂等键 + 项目身份查找原生 302 放大任务；个人模式以空项目标识匹配无项目任务。验证任务类型、准入种类和已确认报价标记，只返回 `found`、任务 ID、受限状态和原报价总额；响应 `Cache-Control: no-store`。不返回令牌、原始请求、供应商响应或媒体 URL，不执行任务创建、收费、供应商调用、补偿、发布或恢复写入。跨 actor/项目、其他任务种类或伪造键不能取得任务信息；无 `idempotencyKey` 的原列表接口保持现状。
- `found=false` 代表当前查询未见持久任务，**不是**未发送证明。标记继续保留，界面只提供再次查询/任务记录入口；不自动清除、换键或重新付费。服务端查询故障、撤权或离线也保持未决。
- 查到处理中或 `submission-unknown` 时只接原任务轮询/状态页，不重新发送 POST。查到服务端已确认终态后可清除对应标记；成功结果仍需按原任务的受权结果版本/投影展示，不从该只读接口直接创建画布图片。
- 同键原任务的报价与扣费保持原值，配置或报价令牌随后过期不影响查询。查无任务的长尾尝试需要另设可审计的人工/服务端确认流程；不能用固定等待时长推断安全重试。

## 验证

先以真实 POST＋隔离 PostgreSQL 做服务端 RED：本人 exact key 可见原任务状态与报价；另一用户/项目、错误任务种类和无任务不可越权；每次查询前后任务、账本与外部发送计数不变。再用真实画布组件 RED 验证：刷新后原标记仍阻止新报价，找到原任务只按任务 ID 跟进，查无任务/网络错误继续阻断，终态才清标记；浏览器存储失败不发生付费 POST。最后按原计划补类型、lint、全量回归、浏览器及云端门禁；局部绿灯不是发布许可。
