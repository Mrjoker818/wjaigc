# 供应商生成与视频任务可靠性设计

**日期：** 2026-08-02  
**范围：** 统一修复顺序第 1 项：供应商图像生成、视频生成、任务状态、超时/取消、积分扣除与退款一致性。  
**不在本阶段：** 图片浮动工具栏、底部工具栏、管理员、用户、支付 UI 的独立功能修复；这些仅接受本阶段任务基础设施带来的回归验证。

## 1. 目标

把图像和视频供应商调用改造成可恢复、可审计、可逐项结算的任务链路。用户选择图片数量 `n=2/3/4` 时，每个槽位都必须有独立状态；任一供应商图片完成后立即显示在画布，不等待同批其他图片完成。

本阶段完成后，以下情形不得再出现：

- 已知供应商失败或审核拒绝，画布仍显示“生成中”或“放大中”。
- 单个图片任务停在低进度且没有超时终态。
- 同一批图片任务按数组顺序串行等待，导致已完成的后续图片不能显示。
- 浏览器、反向代理或部署重启后，供应商已完成的图片无法恢复到项目。
- 同一子任务重复扣费、重复退款，或整批失败覆盖已成功图片。

## 2. 已确认现状与根因

`src/app/api/generate/route.ts` 已按照请求数量循环调用 `submitSingleTask(..., 1, ...)`，因此常规供应商路径可以得到多个上游任务 ID。

`src/components/canvas-workspace.tsx` 已创建与 `outputCount` 相同数量的占位卡并把 `taskIds` 写入其中。但在轮询阶段使用外层 `for (taskIdx...)` 加内部等待循环：第一个任务未完成前，第二个及后续任务不被轮询，所有完成结果还会被收集到 `completedImages`，在所有循环结束后才批量替换占位卡。

这会产生三个可见问题：

1. 供应商先完成的后续图片被前端延迟展示。
2. 前一个任务慢、失败或代理超时，会阻塞同批其他结果。
3. 部分完成、刷新恢复与积分结算难以按单图正确表达。

## 3. 方案选择

采用“独立子任务 + 并发渐进回收”。

### 3.1 任务模型

一次用户点击创建一个逻辑批次，但批次仅用于聚合展示。每张期望图片对应一个稳定槽位：

```text
batchId
  slot 0 -> childTaskId -> providerTaskId -> terminal state
  slot 1 -> childTaskId -> providerTaskId -> terminal state
  slot 2 -> childTaskId -> providerTaskId -> terminal state
  slot 3 -> childTaskId -> providerTaskId -> terminal state
```

- `slotId` 为提交时生成的稳定标识，不依赖图片 URL 或数组索引。
- 一个 `slotId` 最多关联一个活跃子任务；重试创建新子任务时保留同一 `slotId` 与重试链路。
- 子任务持久化：用户、项目、批次、槽位、供应商、模型、规范化请求摘要、上游任务 ID、状态、结果地址、结算状态和时间戳。
- 兼容已存在的单任务记录：没有批次数据的旧任务继续按旧恢复逻辑读取，但不能触发无匹配恢复请求循环。

### 3.2 状态机

子任务只允许下列转换：

```text
created -> submitting -> queued -> processing
processing -> completed
submitting|queued|processing -> failed|cancelled|timeout
```

- `completed` 只能从 `processing` 进入。
- `failed`、`cancelled`、`timeout` 为终态，不能被后续轮询覆写为 `completed`。
- 供应商审核拒绝、参数拒绝、不可重试 HTTP 4xx 必须写入 `failed`，并展示错误码、供应商和模型。
- 连续临时错误只可在明确预算内重试；超过预算必须写入 `timeout` 或 `failed`，不得留下无限 loading。

### 3.3 图像提交流程

1. 前端根据 `n` 创建 `n` 个带 `slotId` 的占位卡，先保存到项目。
2. 前端把批次、槽位和幂等键发送给 `/api/generate`；浏览器请求只等待平台完成提交和持久化，不等待供应商生成。
3. 后端为每个槽位创建或复用一个可审计子任务，并将一张图片的上游请求提交给供应商。
4. 返回每个槽位的 `childTaskId`、`providerTaskId`（如已知）、供应商、模型和初始状态。
5. 前端为全部子任务并发订阅 SSE；SSE 不可用时，对全部未终态子任务并发短轮询。
6. 任一子任务返回结果即持久化结果地址、替换其匹配的占位卡、保存项目并保留其他槽位继续处理。
7. 一个槽位失败只把该占位卡改为失败终态和可重试入口；不得删除同批已完成图片。

供应商若只支持“一个请求生成多张、最后统一返回”，平台仍必须创建可恢复的批次与槽位。若供应商不能提供每张结果的上游状态，UI 明确标记“供应商批量返回”；该例外不得让浏览器长连接等待，服务端负责持续恢复和写入最终槽位结果。

### 3.4 视频流程

视频沿用同一状态机、超时、取消、持久化和结算规则，但一个视频镜头默认对应一个槽位。多镜头或延长任务使用父任务聚合、子任务独立终态。视频卡片在失败、取消和超时必须保留在画布，以可读的终态替代静默消失。

### 3.5 结算与退款

- 积分消耗、退款和子任务终态使用数据库条件更新，保证每个子任务至多扣一次、至多退一次。
- 批次整体状态只做汇总，不作为扣费或退款依据。
- 部分成功时，成功子任务保留已扣积分；失败、取消或超时子任务按其最终状态退款。
- 相同 `userId + idempotencyKey + 请求摘要` 返回同一批次；相同 key 但摘要不同返回冲突，不得创建新任务。

### 3.6 恢复、取消和可观测性

- 画布刷新后按 `batchId + slotId` 恢复每张占位卡与终态结果。
- 恢复逻辑仅对未终态、具备合法任务 ID 的槽位发起轮询；无匹配旧占位卡只标记为遗留失败或待人工处理，不得在渲染循环中反复调用恢复接口。
- 取消请求作用于单个槽位或整个批次；批次取消只取消尚未终态的子任务。
- 每个事件记录 `requestId`、`batchId`、`slotId`、`childTaskId`、`providerTaskId`、`providerId`、`modelId`、状态转换、耗时和结算状态。
- 不记录 API Key、密码、访问令牌或图片二进制内容。

## 4. 代码边界

预计改动限于以下边界，避免重写已有画布和提供商适配层：

- `src/app/api/generate/route.ts`：提交响应、批次/槽位任务持久化、幂等和子任务结算。
- `src/app/api/poll-task/route.ts`：单槽位终态、部分结果、恢复和终态保护。
- `src/components/canvas-workspace.tsx`：并发轮询、按 `slotId` 替换占位卡、部分完成和失败保留。
- `src/lib/task-registry.ts` 与云端任务持久化帮助器：状态转换、终态保护和恢复查询。
- 对应 API、lib、组件和 Playwright 回归测试。

现有提供商协议适配、图片模型能力矩阵、底部工具栏布局和管理员页面不在本阶段重构范围。

## 5. 测试与验收

先建立失败测试，再修改实现。验收必须包含真实已部署供应商任务和本地确定性测试。

### 自动化

- `n=2/3/4` 返回同数量槽位和独立子任务。
- 后续槽位先完成时，先替换对应占位卡，不依赖前序槽位完成。
- 部分成功不会删除已完成图片。
- 失败、审核拒绝、取消、超时均写入终态，不能重新显示 processing。
- 刷新/恢复不重复提交供应商任务，不产生恢复请求风暴。
- 并发重复提交只创建一个批次；积分与退款最多各一次。
- 视频卡片失败、取消、超时不消失。

### 真实浏览器

- 为每个可用非 FHL/虚宝图像供应商至少执行一个最小任务。
- 对至少一个稳定图像模型执行 `n=2`、`n=3`、`n=4`，记录逐张落图时间、`taskId`、供应商任务 ID、结果数量和积分流水。
- 验证一张失败、另一个成功的部分失败情形。
- 在处理中刷新页面，验证已完成图片和未完成槽位恢复。
- 为至少一个视频模型验证提交、处理、完成、失败/取消、结果保留和下载。

通过标准：请求数量、子任务数量、最终图片/视频数量和结算数量一致；每个终态可审计；没有卡死 processing、静默消失或重复结算。

## 6. 风险与控制

- 多任务并发可能触发供应商限流：为每个 provider/model 设置有界并发，而非无限并发。
- 有些供应商只能批量返回：保留批量返回标识，避免伪造逐张进度；平台仍保持后台可恢复。
- 旧任务数据可能缺少槽位信息：使用兼容读取，不对旧数据批量迁移或删除。
- 数据库不可用时禁止向供应商发起付费任务；避免产生无归属、不可退款的上游任务。
