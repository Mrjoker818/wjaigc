# 302 放大双标签提交防重设计（2026-09-28）

状态：本地实现候选；实际画布双标签已在隔离本机应用与浏览器拦截层通过，云端真实身份/付费、独立复审和发布门禁尚未完成，未放行。承接[刷新恢复设计](2026-09-28-302-upscale-submission-recovery-design.md)，仅覆盖已确认报价的原生 302 放大。Pear 分层验证已从本目标移除；PSD 核心不变。

## 现象与根因

两个同源标签可以先后读到“当前图片无未决标记”，随后各自拿到不同随机幂等键和报价。现有浏览器标记按随机键分项保存，`setItem` 后自读只能证明单项写入，不能原子争夺源图。服务端唯一索引只约束 `(user_id, idempotency_key)`；不同键可各建任务、各扣费、各发送供应商。既有真库用例证明同键并发只收一次，并允许首个任务结束后用新键再做一次，但未证明双标签首次确认安全。

## 方案比较

1. 只增加浏览器 `storage` 事件或固定键读写：检查与写入之间仍有竞态，不能作为计费保护。
2. 只加服务端活跃任务排他：覆盖不同浏览器并发，但第一个极速完成后，另一个已持有报价的标签仍可能新建任务；同源用户体验也难以恢复原任务。
3. 浏览器同源锁＋服务端事务活跃任务排他：同一浏览器的两个标签在写标记前串行；不同浏览器即使持不同键，服务端也在扣费之前拦截同时活跃的相同请求。采用此方案。跨设备“首任务已结束、第二设备持旧报价才到达”的情形无法仅凭活跃态区分用户主动重复，须在完整报价/意图合同另行解决，不宣称全局 exactly-once。

## 合同与边界

- 浏览器只针对已确认报价的 302 放大，在调用付费 POST 前申请同源、同 actor、项目、源图及源版本的独占 Web Lock；锁内重读未决标记，发现任何同 actor、同源未决尝试即只读核对，不另发付费 POST。锁内写入原最小标记并确认可读，随后才发 POST；标记在服务端终态确认前保留。锁 API 不可用、拒绝或存储异常时不发送付费 POST，也不把浏览器锁当作服务端防线。其他放大路径保持原合同。
- 服务端只对 `requested-302-upscale` 任务增加可选的活跃请求身份护栏：身份是服务端按 actor 和原请求计算的 `inputIdentityDigest`，不由客户端提供。原有同键重放先处理；随后在同一计费事务内按 actor＋该身份取得 advisory transaction lock，查询已有 `queued/pending/processing` 且同 admission kind 的任务。若是不同键，返回 409 `IMAGE_EDIT_ACTIVE_ATTEMPT`，只携本人该项目的原任务 ID、原随机键和状态；不建第二任务、不扣费、不发供应商、不修改原任务。已终结任务不阻止用户主动取得新报价再运行。
- 第二标签在收到该冲突后删除自己未被受理的标记，改存原任务的最小标记并走原精确只读恢复；任何响应丢失、原任务查询不到或凭证异常均保留未决状态，不用新键重试。返回的原随机键只用来查询，不重新 POST。
- 不建立持久“源图唯一”约束，以免把相同源图不同操作参数、不同用户、不同项目或已完成后主动重做都误判为重复。事务故障回滚时没有扣费或任务落库，但客户端仍不能凭 `found:false` 推断未发送。

## 验证与未覆盖

- 先在隔离 PostgreSQL 中持住第一笔供应商 POST，第二笔用不同键但相同请求身份并发提交；观察 409、仅一任务/一条消费/一次发送。首任务完成后用新键再次提交仍能成功。变更参数、用户或项目不应被错误合并。模拟报价令牌场景，拒绝不得泄露另一用户的任务。
- 在真实画布组件双实例/共享浏览器存储测试中，使两次确认同时到达锁申请前，证明只有一个付费 POST；锁不可用、丢响应及冲突转原任务均不触发第二笔。
- 再跑相邻单元/真库、非增量类型检查、限定 lint、浏览器双标签与刷新、完整保护门禁。局部通过不代表真实 Cookie、云端供应商、全平台计费或发布门禁通过。
