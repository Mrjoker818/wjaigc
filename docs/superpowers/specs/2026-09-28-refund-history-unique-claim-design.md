# 历史重复退款兼容与新退款唯一性设计

## 问题与范围

当前 `ensureCoreTables()` 对所有有任务身份的退款流水建立表达式唯一索引。若历史数据已有相同 `task_id` 或旧式 `reference_id` 的多条退款，启动时 PostgreSQL 以 `23505` 拒绝建索引。不能删除、合并、改写历史流水，也不能为启动而取消新退款的唯一性。此设计只处理通用退款身份迁移，不等于图像编辑或全平台发布验收。

## 方案选择

方案 A：只对新 ID 建局部唯一索引。部署简单，但旧任务的通用退款、云任务退款和其他直接写入者仍可能跨路径重复，不采用。

方案 B：应用层逐一加锁和查重。需要证明每个直接 SQL 写入者均已改造，且新写入路径会持续绕过，不能作为唯一屏障，不采用。

方案 C（选定）：保留原账本，新增退款身份占位表，主键为 `COALESCE(NULLIF(task_id,''), NULLIF(reference_id,''))`。迁移在单一 PostgreSQL 事务中锁定账本、以 `SELECT DISTINCT` 为所有已有身份建占位、安装 `BEFORE INSERT OR UPDATE` 触发器，再提交。旧重复只占一个身份，不更改旧行；任意后续写入者插入同身份，或把旧行改成新的同身份时，触发器插入占位发生主键冲突，原 SQL 和同一事务的余额更新一并回滚。更新时若有效身份不变，不重复占位；已占用的旧身份即使相关旧行删除或改名也不自动释放。没有任务身份的旧式匿名退款不在本设计的幂等键范围内，其风险另列审计。

## 合同与故障处理

- 旧索引已存在的部署保留它，兼容旧错误约束名；没有索引且历史有重复的部署不再尝试强建失败的全历史唯一索引。原 `idx_credit_tx_task_type_once` 同时含 `ctx_refund_%`，也会被这种历史冲突破坏；新部署改建只针对 `ctx_charge_%` 的消费唯一索引，退款由占位主键负责。已存在的原索引不删除。占位主键是新写入者的共同数据库屏障，不能把触发器或占位表删掉后仍宣称安全。
- 迁移事务持有账本写锁直到回填、函数及触发器安装完成；并发启动必须串行且幂等。迁移失败必须整体回滚。实际启动初始化可异步且非致命，因此所有退款入口还必须先等待 `ensureCoreTables()`；迁移失败时退款写入 fail-closed，不能以“跳过索引”继续退款。
- 首次安装后须以占位表主键和启用的触发器为就绪标记；普通复启只读检查，不再次锁表或回扫账本。若标记损坏或触发器禁用，不能以“表存在”冒充就绪。
- 新退款与余额变更必须保持原有单 SQL/事务原子性。云任务终态结算捕获占位主键冲突后，只能根据唯一且同用户同金额的已有退款对账；旧历史多条同身份不得返回“已成功退款”。
- **禁止旧、新版本并行处理退款。** 旧版 `refundCredits` 在事务写账本失败后仍可能退化为单独更新余额，之后再尝试记账并吞掉失败；新触发器虽然拦下重复账本行，却不能阻止旧进程把余额多加一次。发布时须停写／排空并确认全部旧实例退出，才允许迁移与新版退款入口放流；如果不能证明旧实例已退出，发布保持 BLOCK。仅靠混合版本“请求报错”或数据库唯一性不足以保证余额正确。
- 保持两条非唯一退款检索索引（`task_id`、`reference_id`），避免历史回填后普通与云任务对账仅凭全表扫描；不能把它们改成历史唯一索引。
- 占位只保存身份，不复制金额、用户、凭证或原图。历史冲突只用于启动诊断；未经账务审计不得自动补偿、删除或变更余额。既有可能重复的旧流水不会被本迁移“修复”。

## 验证与发布门槛

先在全新 loopback 专用 PostgreSQL 库 RED→GREEN 验证：旧重复保留且可启动、第三笔同身份被拒、新身份可写、跨连接并发同身份仅一笔、余额与流水原子一致、普通退款与云任务退款互相对账、重复旧历史不可被误报为单次退款。再跑目标 ESLint/TypeScript、相关真库套件、保护基线和全量回归；未过的门槛继续 BLOCK。仅在沙箱审计历史冲突分布、迁移锁耗时和混合版本切换行为后，才考虑部署；不连接业务库进行本地测试。
